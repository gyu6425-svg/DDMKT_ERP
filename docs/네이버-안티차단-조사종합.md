# 네이버 안티차단 — 조사·독립검증 종합 (2026-07-29)

> 브랜치 sub3에서 조사. 리서처·리뷰어·플래너 3역할 독립검증 + QA로 도출. **미커밋 기록 문서.**
> 계기: '마이클의 정보 세상' 카페 발행이 회사 단일 IP 과부하로 1단계 인증(비정상 활동) 유발.

## 0. 한 줄 결론
- **마이클 차단은 "발행" 문제**이고, 발행은 이미 실브라우저라 **라이브러리/TLS지문과 무관**. 원인은 IP·빈도·행동 계층.
- 근본 해법은 위장 강화가 아니라 **발행 강도 하향 + 계정↔IP 안정성**. 단, 계정 상관 회피·재인증 무력화(=플랫폼 안전장치 우회)는 우리가 최적화하지 않는다(§4).
- 조사는 사실상 완료. 남은 건 엔지니어링이 아니라 **운영 강도에 대한 사업 판단**.

## 1. 시스템 경로 지도 (코드로 확정)

| 경로 | 네이버로 나가는 클라이언트 | 근거 |
|---|---|---|
| **발행** (마이클 등) | 실크롬 — Playwright CDP attach. `requests`는 Supabase 전용 | `publish_cafe.py:242` `connect_over_cdp`; requests 대상은 `{SUPABASE_URL}/...`뿐 |
| **순위 조회** (크롤러) | 생짜 `requests` (UA 헤더만) 직접 SERP 호출 | `blog_rank_crawler.py:1464` `_fetch_html=requests.get(UA)`; `run_today_loop.py:26` `c._fetch_html`; 호스트 `m.search.naver.com` |
| **인기글 스캔** (발행 전) | Node `fetch` (Cloudflare/로컬 :8787) | `cafePopular.mjs:49` fetch, `BLOCK_RE`; `rank.ts:2` CF 데이터센터 IP 차단 우려 |

> ⚠️ 이전 워딩 정정: "requests는 Supabase 전용"은 **발행 경로(`publish_cafe.py`) 한정** 진술이었음(전역 아님). 조회 경로는 requests로 네이버 직접 호출이 맞음. 두 진술은 서로 다른 파일이라 모순 아님.

## 2. 독립검증으로 확정된 사실
- 발행 = 사람 1회 로그인한 크롬에 CDP로 붙어 조종(`publish_cafe.py:5-6` docstring). 자동화 launch 아님.
- `truststore` = OS 신뢰저장소 기반 **SSL 인증서 검증**용(윈도 백신 MITM 대응). **TLS 지문 위장과 무관**(`requirements.txt:5`).
- **공식 API 이미 라이브 사용 중**: 검색광고 searchad(`naver-keywords.ts`, 키워드 볼륨), webkr(`measure_web_rank`, 웹문서 순위). 통합탭·블로그탭·카페 순위만 스크래핑 — **API가 화면 순서와 달라서**지 설계 미비 아님(`blog_rank_crawler.py:1366` 주석 자백).
- 마이클의 정보세상 발행 = 더맨/theman 스택 **크롬 포트 9224**(`run_cafe_listener_theman.bat`). (9225는 별개 ddnusu.) IP는 그 리스너가 도는 물리 PC가 결정, 코드에 프록시 없음.
- 기존 방어 인벤토리(실재): 발행 간격 `CAFE_MIN_GAP_MIN`(20~30분 랜덤)·작성시간 하한 `CAFE_MIN_SECONDS`(330s)·사람흉내 타이핑/오타연출·이미지 미세변형 / 조회 `REQUEST_DELAY`(3.5s)+지터·`BLOCK_REST`(6건마다 40s)·즉시검색 양보·`crawl_status` 코디네이션.

## 3. 초기 분석에서 정정된 결론 (4건)
1. **"IP발 차단 단정" → 철회.** `is_blocked`가 상태코드만 봐(`run_today_loop.py`) 403이 IP인지·지문인지·레이트인지 **코드가 구분 못 함**. → "원인 미확정".
2. **"핫스팟=해결" → 하향.** 모바일 CGNAT 공유 IP는 다계정 상관 위험 + IP 급변 시 재인증 유발. **본질은 IP 종류가 아니라 계정↔IP 안정 바인딩 + 저빈도 + 인간형 패턴.**
3. **"진짜 크롬=탐지 자유" → 과신.** CDP `Runtime.enable` leak 등 자동화 흔적 벡터 실재. 단 카페 글쓰기가 거기까지 당한 징후 없음.
4. **"공식 API 안 씀" → 사실 오류.** 이미 최적점에서 쓰고 있음(§2). 새 API 도입 여지 거의 없음.

## 4. 판단 경계 — 도울 수 있는 것 / 없는 것

**돕지 않는 것 (플랫폼 안전장치 무력화):**
- 여러 계정을 하나의 운영 주체로 묶이지 않게 하는 **IP 토폴로지 설계**(계정↔IP 1:1 등) — 계정 상관관계 탐지는 정확히 이걸 잡으려 존재.
- 자동 글쓰기의 **재인증 챌린지를 stealth(Patchright/rebrowser)로 무력화**.
- SERP 봇탐지를 **TLS 지문 스푸핑(curl_cffi)으로 우회**.
- 이유: 계정이 진짜 클라이언트 브랜드 소유라도, 기법 자체가 그 안전장치가 겨냥하는 대상. 리스크 비대칭(적발 시 손실이 클라이언트 공식 채널에 떨어지고, 자산 누적일수록 기대손실↑; 매크로 운영에 대한 민사 대응 전례).

**돕는 것 (정당한 운영·관측):**
- 순위 조회의 **관측성/헬스 로깅**(아래 §5), 공식 API 활용 확대, 정중한 레이트리밋·백오프.
- 발행 **강도 하향 설계**: 계정당 발행 상한·간격·원고 다양성("덜 하기" 방향).
- 정식 광고상품(파워콘텐츠 등) 검토.

## 5. (선택) 순위 조회 경로 — 진단 관측성만
차단 원인 사후 귀인을 위해 **로깅만** 보강(스푸핑 아님):
- `classify_block(resp,ctx)`: `status·final_url·body_hash(앞2KB)·Retry-After·req_idx·ip_age·cookie_age`. **status 200이어도 body로 차단 페이지 판정**.
- 판별표(진단용): 새 IP 1요청째부터 차단→헤더이전 계층 / 수백건 뒤 열화→빈도 / 쿨다운 복구→레이트 / IP 교체 즉시 복구→IP 평판.
- ⚠️ 진단이 "지문"을 지목해도 **조치는 스푸핑이 아니라 "그 조각 수집 강도↓ / API 의존↑"**(§4 경계 유지).

## 6. 다음 단계 & "지금 충분한가"
**충분하다.** 조사·검증은 완료됐고 병목은 코드가 아니라 운영 강도다. 남은 정당한 액션은 작고 선택적:
- (A) SERP 크롤러 `classify_block` 관측성 로깅 — 언제 물러설지 판단용.
- (B) 마이클 발행 강도 하향 — 계정당 상한·간격·원고 다양성 설정 조정.
- (C) 이 문서 커밋 여부 결정.
