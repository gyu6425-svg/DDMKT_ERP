> 브랜치 sub3 작성. **미구현 · 설계 단계.**
> 목적: 광고 건별로 받은 **클라이언트 채널**에 롱폼(유튜브) / 숏폼(쇼츠·릴스)을 자동 업로드.

- 인스타 릴스는 **별개 API·별개 심사** — 유튜브와 한 몸으로 묶지 말 것.

## 1. 제약 먼저 (설계보다 이게 중요)

### 1-1. ⚠️ API 감사 미통과 = 업로드 영상이 **강제 비공개** (사실 확인됨)
**2020-07-28 이후 생성된 미감사(unverified) 프로젝트가 `videos.insert` 로 올린 영상은 private 로 잠긴다.** 수동 공개 전환 필요.
- 광고 건은 공개가 필수 → **감사 통과가 사실상 필수 요건**.
- 감사 전까지 운영 가능한 범위: "업로드 + 메타데이터(제목·설명·태그·썸네일)까지 자동, **공개 전환만 수동**".
- 신청: *YouTube API Services — Audit and Quota Extension Form* (감사와 할당량 증량이 **같은 폼**).

### 1-1-b. ⚠️ 심사는 **두 개**다 (혼동 주의)
| | ① Google OAuth 검증 | ② YouTube API 감사 |
|---|---|---|
| 어디서 | Cloud Console → OAuth 동의 화면 | 별도 구글 폼 |
| 무엇을 푸나 | "미검증 앱" 경고 제거, refresh token 지속 | **비공개 잠김 해제 + 할당량 증량** |
| 기간 | 최대 10일 | **수 주 ~ 수 개월** (5개월 사례 보고) |

**둘 다 필요하고, ②가 진짜 관문이며 훨씬 오래 걸린다.**

**공통 준비물:**
1. **소유 도메인** — Search Console 소유권 검증 필요.
   ⚠️ `ddmkt-erp.pages.dev` 는 공용 서브도메인이라 부적합 — **회사 도메인 확보 권장**(심사 통과율·신뢰도).
2. **홈페이지** — 그 도메인에서 앱 기능 설명.
3. **개인정보처리방침** — 같은 도메인·홈페이지에서 링크. 템플릿 복붙은 반려 사유. YouTube 데이터의 **저장 항목·보관기간·파기** 실제 기재.
4. **이용약관**
5. **데모 영상** — YouTube 미등록(unlisted) 업로드 후 링크 제출. **영어**로, OAuth 동의 화면부터 **각 스코프의 실제 사용 장면까지** 전부. → **반려 사유 1위**(동의화면만 찍으면 탈락).
6. **사용 사례 + 예상 물량 + 사업적 정당성**

**우리 케이스 서술 전략** — "대행사 소셜미디어 관리 도구"(Hootsuite·Buffer 선례 있는 카테고리):
- 광고주가 **자기 채널의 관리자 권한을 위임**, 우리는 그 범위 내에서만 업로드
- 광고주가 언제든 권한 회수 가능(오프보딩 경로 명시)
- 저장 데이터(refresh token·채널ID·업로드 결과)와 보관기간 명시
- 스코프는 **`youtube.upload` 최소한으로** — 과다 요청은 반려 사유

**순서**: 앱/UI 구현(스크린샷·데모영상 필요) → 도메인+홈페이지+방침 → 데모영상 → ① OAuth 검증 → ② 감사 신청 → 대기 → 공개 해제

### 1-2. 할당량 — 하루 **6건**이 상한 (채널별 아님, **프로젝트 단위**)
| 작업 | units |
|---|---|
| `videos.insert` (업로드) | **1,600** |
| `thumbnails.set` | 50 |
| `playlistItems.insert` | 50 |
| `videos.list` (조회) | 1 |

- 기본 **10,000 units/day** → **업로드 약 6건/일**.
- **채널을 10개 관리해도 합산 6건.** 대행사 물량이면 즉시 부족 → 증량 신청 필수.
- 설계 반영: 큐에 **일일 업로드 카운터 + 할당량 가드**를 반드시 넣는다(초과 시 다음날로 이월).

### 1-3. OAuth — 채널이 유동적인 게 핵심 변수
광고 건마다 채널이 바뀌므로 **채널당 인증 확보 방식**이 설계를 좌우한다.

| 방식 | 내용 | 평가 |
|---|---|---|
| (A) 클라이언트 직접 동의 | 건마다 동의 링크 발송 | 이탈·번거로움 |
| **(B) 우리 계정을 채널 관리자로 초대** ⭐ | 클라이언트가 YouTube에서 우리 구글 계정을 **관리자(Manager)** 추가 → 우리가 OAuth 시 **채널 선택**해 채널별 토큰 발급 | **권장.** 클라이언트가 언제든 권한 회수 가능(통제권 유지) |

- (B) 채택. 계약 종료 시 클라이언트가 관리자 권한만 회수하면 자동으로 접근 차단 — 깔끔한 오프보딩.
- ⚠️ `onBehalfOfContentOwner` 파라미터는 **MCN/CMS 파트너 전용** — 우리 케이스엔 해당 없음.

### 1-4. OAuth 앱 게시 상태
- **테스트(Testing) 모드**: refresh token이 **7일마다 만료** → 무인 자동화 불가. 테스트 유저 100명 상한.
- → **게시(Published) 상태 전환 필수.** 그래야 refresh token이 지속된다.
- `youtube.upload` 는 민감 스코프 → 미검증 상태면 동의 화면에 경고 표시.

### 1-5. 숏폼은 플랫폼마다 다름
| 대상 | 방법 | 비고 |
|---|---|---|
| YouTube 롱폼 | `videos.insert` | 기준 경로 |
| **YouTube 쇼츠** | **별도 API 없음** — 세로(9:16) + 60초 이하로 올리면 자동 인식 | 롱폼과 동일 코드 |
| **인스타 릴스** | **Instagram Graph API** (완전 별개) | §6 참조 |

## 1-6. 도메인 — 실측 현황과 조치 (2026-07-31 확인)

심사 전제인 "소유 도메인"은 **이미 보유 중**(`ddmkt.com`, 회사 메일 도메인). 새로 살 것 없음.

| 항목 | 실측 상태 |
|---|---|
| ddmkt.com 네임서버 | **호스트코코아**(hostcocoa.com) — Cloudflare 아님 |
| MX(메일) | **네이버 웍스**(worksmobile) — ⚠️ **절대 건드리지 말 것** |
| www.ddmkt.com | AWS CloudFront에 회사 홈페이지 운영 중 |
| erp.ddmkt.com | **비어있음** → 여기 붙이면 됨 |

**조치: 네임서버 이전 금지, CNAME 한 줄만 추가.**
DNS를 Cloudflare로 옮기면 네이버 웍스 MX·SPF·DKIM 재설정 필요 → **회사 메일 중단 위험**. 그럴 이유 없음.

**설정 순서 (⚠️ 순서 틀리면 522 에러):**
1. **먼저** Cloudflare 대시보드 → Workers & Pages → `ddmkt-erp` → **Custom domains** → `erp.ddmkt.com` 등록
2. **그다음** 호스트코코아 DNS 관리 → CNAME 추가: 호스트 `erp` → 값 `ddmkt-erp.pages.dev`
3. 전파 10분~1시간, SSL 자동 발급(5~15분)

**비용: $0.** 커스텀 도메인·SSL 모두 Free 플랜 포함. 도메인 갱신비도 기존 그대로.
- 기존 `ddmkt-erp.pages.dev` 는 계속 작동 → 코드에 박힌 15곳(`cafe_kw_probe.py` `_AD_ENDPOINT` 등) 급히 안 바꿔도 됨.
- 외부 DNS라 존 단위 기능(WAF·페이지룰)은 미사용 — 현재도 안 쓰므로 실손해 없음. CDN·SSL은 정상.
- 심사용 홈페이지는 **www.ddmkt.com 기존 사이트 활용** + `/privacy`, `/terms` 추가면 충족(같은 등록 도메인이라 세트 인정).

## 2. 아키텍처

```
웹 UI(채널·영상·제목·설명·태그·공개설정·예약일)
   └─ 영상 파일 업로드 → Cloudflare R2 (대용량·이그레스 무료)
   └─ 큐 적재 → video_upload_queue (pending) [Supabase]
                     ↓ 폴링
   로컬 워커(파이썬)  ─ CAS claim(pending→processing)
                     ─ 채널 토큰 조회 → access token 갱신
                     ─ R2에서 영상 다운로드(boto3, 이그레스 무료)
                     ─ YouTube resumable upload
                     ─ 썸네일·재생목록(선택)
                     └─ 결과 기록(videoId·상태·할당량 소비)
```

### 왜 업로드를 로컬 워커가 하는가
- 영상 파일이 크다(수백MB~GB). **Cloudflare Workers는 실행시간·메모리 제한**으로 부적합.
- CF의 역할은 **토큰 발급/갱신·OAuth 콜백**까지만(= `client_secret` 서버 보관).
- 카페 발행(`publish_listener.py`)과 **동일한 큐·워커 패턴** 재사용.

### 영상 파일 저장소 — **Cloudflare R2** (결정)
영상은 DB가 아니라 **오브젝트 스토리지** 문제. Supabase Storage는 플랜별 파일 크기 상한(무료 기본 50MB)이 있어 롱폼 원본에 부적합.

| 서비스 | 무료 | 이후 | 이그레스 | 비고 |
|---|---|---|---|---|
| **Cloudflare R2** ⭐ | 10GB | ~$0.015/GB·월 | **$0** | 이미 CF 사용중, S3 호환 |
| Backblaze B2 | 10GB | $6/TB·월 | 일부무료 | 저렴 |
| Wasabi | – | $6.99/TB·월 | $0 | 90일 최소보관 |
| AWS S3 | – | $23/TB·월 | **유료(비쌈)** | 이그레스가 독 |
| Supabase Pro | 100GB 포함 | $25/월~ | 유료 | 대용량엔 비쌈 |

**R2 채택 이유:**
1. **이그레스 무료** — 워커가 영상을 내려받는 게 곧 이그레스. S3면 지속 비용, R2는 0원.
2. **이미 Cloudflare 계정** — Pages 함수에서 바로 접근, 인증 통합.
3. ⭐ **인스타 릴스 요건 동시 해결** — 릴스는 "공개 접근 가능한 URL" 필수(§6). R2는 공개 버킷/커스텀 도메인 가능. Supabase private 버킷이면 매번 서명 URL 필요.
- S3 호환 → 파이썬 `boto3` 그대로. 단일 객체 5TB(대용량은 멀티파트).

**역할 분리**: **R2 = 영상 파일 전용** / **Supabase = 큐·토큰·메타데이터 전용**.
```
웹 UI → 영상 파일 → R2
      → 메타데이터·큐 → Supabase
로컬 워커 → R2에서 다운로드(이그레스 무료) → YouTube 업로드
```

## 3. DB 스키마 (초안)

기존 `cafe_publish_queue` 컨벤션(상태값·CAS·좀비회수·attempts)을 그대로 따른다.

```sql
-- docs/video-upload-queue.sql (예정)

-- ① 채널 자격증명 (채널별 refresh token)
create table if not exists public.video_channels (
    id uuid primary key default gen_random_uuid(),
    created_at timestamptz not null default now(),
    platform text not null,                 -- 'youtube' | 'instagram'
    channel_id text not null,               -- YouTube channelId / IG user id
    channel_name text,
    client_id uuid,                         -- 어느 광고주 건인지(내부 고객 테이블 참조)
    refresh_token text not null,            -- ⚠️ 암호화 저장 검토(§7)
    scopes text,
    status text not null default 'active',  -- active | revoked | expired
    last_used_at timestamptz,
    unique (platform, channel_id)
);

-- ② 업로드 큐
create table if not exists public.video_upload_queue (
    id uuid primary key default gen_random_uuid(),
    created_at timestamptz not null default now(),
    platform text not null default 'youtube',   -- youtube | instagram
    channel_ref uuid references public.video_channels(id),
    kind text not null default 'long',           -- long | short | reels
    title text not null,
    description text,
    tags text[],
    category_id text,                            -- YouTube 카테고리
    privacy text not null default 'private',     -- private | unlisted | public
                                                 -- ⚠️ 감사 통과 전에는 무조건 private로 강제됨
    video_path text,                             -- Storage 경로 또는 로컬/외부 URL
    thumbnail_path text,
    publish_at timestamptz,                      -- 예약 공개(YouTube publishAt)
    scheduled_at timestamptz,                    -- 워커가 언제 집을지
    status text not null default 'pending',      -- pending | processing | uploaded | done | fail
    video_id text,                               -- 업로드 결과 videoId
    posted_url text,
    reason text,
    attempts int not null default 0,
    claimed_at timestamptz,
    done_at timestamptz
);
create index if not exists vuq_status_idx on public.video_upload_queue (status, created_at);
create index if not exists vuq_platform_status_idx on public.video_upload_queue (platform, status, created_at);

-- ③ 할당량 소비 기록 (하루 6건 가드)
create table if not exists public.video_quota_log (
    id uuid primary key default gen_random_uuid(),
    created_at timestamptz not null default now(),
    day date not null default (now() at time zone 'Asia/Seoul')::date,
    platform text not null default 'youtube',
    units int not null,                          -- videos.insert=1600 등
    queue_ref uuid
);
create index if not exists vql_day_idx on public.video_quota_log (day, platform);

-- RLS: 기존 컨벤션과 동일(내부 전용)
alter table public.video_channels     enable row level security;
alter table public.video_upload_queue enable row level security;
alter table public.video_quota_log    enable row level security;
-- create policy ... for all to authenticated using (public.is_internal()) with check (public.is_internal());
```

> ⚠️ 실제 적용 전 `is_internal()` 정의 확인 — `client_id IS NULL AND role NOT IN('reporter','viewer')` (축약 금지, `docs/enable-login-rls.sql`).

## 4. 워커 설계 (`crawler/video_pub/` 예정)

카페 리스너(`publish_listener.py`)에서 검증된 방어를 그대로 이식:

| 장치 | 내용 | 출처 |
|---|---|---|
| **CAS claim** | `pending→processing` 을 `expect="pending"` 으로 원자적 선점. 실패 시 건너뜀(중복 업로드 방지) | `publish_listener.py:266-269` |
| **좀비 회수** | `processing` 인데 `claimed_at` 이 오래된 행 → `pending` 복구 | `:178-189` `_reap_stale` |
| **attempts 상한** | 일시오류 재시도, `MAX_ATTEMPTS`(기본 3) 초과 시 `fail` | `:321-326` |
| **KST 벽시계** | `done_at/claimed_at` 은 naive KST 규약(UTC 쓰면 9시간 skew) | `:79-84` |
| **인증** | `sb_auth.py` 재사용(publishable+내부JWT, 없으면 서비스키 폴백) | `crawler/cafe_pub/sb_auth.py` |

**신규로 필요한 것:**
- **할당량 가드**: 업로드 전 `video_quota_log` 로 당일 소비 합산 → 10,000 초과 예상이면 집지 않고 대기(다음날 이월). 로그로 남겨 "왜 안 올라갔는지" 보이게.
- **resumable upload**: 대용량·네트워크 끊김 대비. 중단 시 이어올리기.
- **토큰 갱신**: `refresh_token` → access token. `sb_auth.py` 의 만료 2분 전 갱신 패턴 그대로.
- **업로드 후 검증**: `videos.list` 로 처리 상태 확인(1 unit). `uploaded→done` 전이.

|---|---|---|
| **0-a. 즉시** | **회사 도메인 + 홈페이지 + 개인정보처리방침·약관** 준비 | 심사 전제조건 |
| **0-b. 신청** | 구글 클라우드 프로젝트 → 데모영상 → **① OAuth 검증(≤10일) + ② 감사·증량 폼** | ②는 수 주~수 개월 → **최대한 빨리** |
| **1. PoC** | OAuth 1회 인증 → refresh token 저장 → 영상 1건 비공개 업로드 성공 | 없음(바로 가능) |
| **2. 스키마·큐** | `video-upload-queue.sql` 적용, 웹 UI에서 큐 적재 | 없음 |
| **3. 워커** | CAS·좀비회수·할당량가드·resumable 구현 | 없음 |
| **4. 채널 온보딩 UI** | 관리자 초대 안내 → OAuth 채널 선택 → 토큰 저장 | 앱 게시 상태 전환 |
| **5. 공개 전환** | 감사 통과 후 `privacy: public` 해제 | **Phase 0 승인 대기** |
| **6. 인스타 릴스** | 별개 API·별개 심사(§6) | 메타 앱 심사 |

→ **Phase 1~4는 감사와 무관하게 지금 바로 진행 가능.** Phase 0을 병렬로 걸어두는 게 핵심.

## 6. 인스타 릴스 (별건)

**유튜브와 한 몸이 아님.** 요구사항이 따로:
- 클라이언트 계정이 **비즈니스/크리에이터(프로페셔널) 계정** + **페이스북 페이지 연결** 필수
- 권한: `instagram_content_publish` 계열 → **메타 앱 심사 + 비즈니스 인증** 필요
- 방식: 파일 직접 업로드가 아니라 **공개 URL을 넘기는** 2단계
  1. 컨테이너 생성 (`media_type=REELS`, `video_url=<공개 URL>`)
  2. 게시 (`media_publish`)
  → 영상을 **공개 접근 가능한 URL**에 올려둬야 함(R2/S3 등). Supabase private 버킷은 서명 URL 필요.
- 레이트리밋: 계정당 24시간 **약 50개** 게시

→ 유튜브 Phase 1~5가 안정된 뒤 별도 Phase로. 스키마는 `platform` 컬럼으로 이미 확장 가능하게 설계됨.

## 7. 보안 — refresh token 취급

`refresh_token` 은 **클라이언트 채널에 대한 지속 접근 권한**이라 사실상 비밀번호급.
- **클라이언트(브라우저)에 절대 노출 금지** — RLS `is_internal()` 로 내부만, 웹 UI는 토큰 값 자체를 조회하지 않게.
- `client_secret` 은 **CF 환경변수**에만(코드·DB 금지) — `naver-keywords.ts` 가 검색광고 키 다루는 방식과 동일.
- 저장 시 **암호화 검토**: Supabase 컬럼 암호화 또는 워커만 아는 키로 봉투 암호화.
- **오프보딩**: 계약 종료 시 `status='revoked'` + 클라이언트에게 관리자 권한 회수 안내.
- ⚠️ 워커 PC의 `.env` 는 `.gitignore` 확인 필수(기존 규칙).

## 8. 확인 필요 / 미결정

1. **롱폼 영상 평균 용량·월 편수** — R2 비용 추정용(저장소는 R2 확정, 비용만 산출).
   참고: 롱폼 100편×500MB ≈ 50GB ≈ **월 600원** 수준(무료 10GB 초과분).
2. **동시 관리 채널 수** — 하루 6건 상한 대비 실제 물량. 증량 신청 근거 자료로도 필요.
3. **영상 제작 주체** — 파일이 이미 있는지, 생성까지 자동화할지(후자면 별도 설계).
4. **예약 공개 사용 여부** — `publishAt` 쓰려면 업로드 시 `privacy=private` 필수(감사 전엔 어차피 private).
5. **감사 신청 주체** — 대행사 명의 프로젝트 1개로 전 클라이언트 커버(권장) vs 클라이언트별 분리.
